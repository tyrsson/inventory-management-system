# ACL Implementation Waypoint — 2026-05-19

**Branch:** `acl-ownership-assertion-aggregates`

---

## What Is Done

### Config system
- `config/autoload/acl.global.php` created. Keyed under `AclInterface::class` (FQCN). Holds empty
  `roles`, `resources`, `allow`, `deny` arrays — these are intentionally empty; modules own their
  own data.
- **Role ownership:**
  - `webware-usermanager` → `Guest`, `Member`
  - `webware-admin` → `Administrator` (parent: `Member`)
  - `webware-acl` → `Developer` (parent: `Administrator`)
- All role identifiers are capitalized consistently across the entire codebase.
- `ArrayUtils::merge()` appends numeric arrays, so duplicate role parents are avoided by
  keeping `roles` in `acl.global.php` empty — modules are the sole owners of their roles.

### AclFactory
- Completely rewritten to build `Laminas\Permissions\Acl\Acl` directly from config. No
  `AclBuilder` dependency for core build path.
- `addRoles()` — topological sort, registers roles with optional parents. ✓
- `addResources()` — flat indexed list of route name strings. ✓
- `applyRules()` — uses `array_is_list()` to distinguish:
  - Flat list `['resource.a', 'resource.b']` → `allow($role, $resource, null)` (no assertion)
  - Associative `['resource.a' => [FQCNs]]` → `allow($role, $resource, null, $assertion)` (with assertion)

### Config shape (canonical)
```php
AclInterface::class => [
    'roles' => [
        'Guest'         => [],
        'Member'        => ['Guest'],
        'Administrator' => ['Member'],
        'Developer'     => ['Administrator'],
    ],
    'resources' => [
        'user.manager.session.read',
        'user.manager.session.create',
    ],
    'allow' => [
        'Guest' => [
            'user.manager.session.read',
            'user.manager.session.create',
        ],
        'Member' => [
            'ims.product.read',                          // no assertion
            'ims.product.update' => [FQCNAssertion::class], // with assertion
        ],
    ],
    'deny' => [],
]
```

### Middleware / routing
- `Acl::isAllowedRoute()` — opt-in model: unregistered routes return `true` (open until
  explicitly protected).
- `RouteMiddleware` sets `RouteResource::class` request attribute (enriched, for ACL) in
  addition to the standard `RouteResult::class` attribute.
- `AuthorizingDispatchMiddleware` replaces upstream `DispatchMiddleware` globally. Reads
  `RouteResource::class`, performs ACL check, short-circuits with redirect on deny.
- `ForbiddenHandler` — default denial response handler, swappable via DI.

### Session / login
- `usermanager` `getAclConfig()` registers `user.manager.session.read` and
  `user.manager.session.create` as resources, and allows both for `Guest`.
- Login page loads correctly. ✓

### Factory fixes
- `UserFactory` and `LoginHandlerFactory` read `$config[AclInterface::class]` (was
  incorrectly `$config['webware-acl']`).
- `webware-admin` `ConfigProvider::getAclConfig()` fixed double-nesting.

## Outstanding / Not Yet Done

### 1. `RouteResource::getPrivilegeId()` — remove or stub
The `applyRules()` and `isAllowedRoute()` path now passes `null` as the privilege
(authorization is on the resource alone). `getPrivilegeId()` (which mapped HTTP method →
`read`/`create`/etc.) is therefore dead code. Options:
- Remove `PrivilegeInterface` implementation entirely from `RouteResource`.
- Or keep the mapping for future fine-grained privilege support but stop calling it.

`Acl::isAllowedRoute()` still calls `$routeResource->getPrivilegeId()` — this call should
be changed to `null` (or removed).

### 2. Route-mapping infrastructure — deletion still pending
The original plan (see `route-resource-acl-implementation.md`) listed 11 files/classes to
delete as part of the route-name-as-resource-ID migration. That cleanup has not happened.
Outstanding deletions include:
- `AuthorizationMiddleware` (and factory)
- `RouteMapManagerHandler` and related middleware
- `SaveRouteMappingCommand` / `DeleteRouteMappingCommand` and handlers
- `RegisterAclRouteMappingsListener` / `RegisterManifestRouteMappingsListener`
- `AclBuiltEvent` route-mapping API methods
- `AclBuilder` route-mapping data path
- `AclRepository` / `AclRepositoryInterface` route-mapping methods (`fetchRouteMappings`,
  `saveRouteMapping`, `deleteRouteMapping`)
- All per-route `AuthorizationMiddleware::class` entries in all five `RouteProvider` files

### 3. Admin UI — "Protect Route" feature
Files 8–14 from the implementation plan (ProtectRouteCommand, ProtectRouteHandler,
ProcessProtectRouteMiddleware, ResourceListHandler modifications, admin template) are not
yet created.

### 4. Module resource/allow configs
Only `webware-usermanager` has resources and allow rules wired. Every other module that
needs ACL protection must add its own `resources` and `allow` sections to its
`getAclConfig()` return value. Current state:
- `webware-usermanager` ✓
- `webware-admin` — has roles only, no resources/allow
- `ims-manifest` — not wired
- `ims-store` — not wired
- `App` module — not wired

### 5. `AclBuilder` / `AclBuiltEvent`
`AclBuilder` still exists and still has the route-mapping data path. It needs to be
stripped down to only what is still used (if anything), or deleted if the direct-from-config
`AclFactory` path makes it entirely redundant.

### 6. Assertion infrastructure
`StoreOwnedResourceAssertion` and the ownership assertion aggregate pattern are not yet
wired to real config `allow` entries — the assertion system works in isolation but has not
been exercised end-to-end with a live request.
